# Wave 0G-L1G — Regenerate the V2 launch candidate with the fixed id scheme

**Verdict: DONE.** `data/v2-candidate/deals-v2.json` was regenerated
deterministically, entirely offline (zero new acquisition), with the
Wave 0G-L1D id-scheme fix applied to every row. Row count, entity
composition, and every non-id field are byte-identical to the original
L0 build — only the `id` string values changed, resolving the 116-row
collision that blocked L1's import. `data/deals.json` is unchanged.

## Why re-running the build alone wasn't enough

`build-v2-launch-candidate.ts`'s `buildUnion()` reconstructs the
59,305-row union mostly by **reading already-serialized `ShadowDeal` JSON**
(`audit/wave0g16/shadow-output/*.json`, `audit/wave0g18/shadow/*.json`,
`audit/wave0g24/shadow/*.json`) — files written before Wave 0G-L1D
existed, with the OLD, collision-prone `.id` already baked in. Only a
small subset of rows (inside `reconstructKiryatFinalUnion()`'s wave20/21
probe replay) call `toShadowDeal()` live during the build. Simply having
the L1D code fix in place would NOT have changed the majority of rows'
ids — they needed to be explicitly recomputed.

## Fix

Added a step at the end of `buildUnion()` (inside the function, not in
`main()` after calling it — matching the same rationale already
established there for coordinate enrichment: both the primary build call
and the internal determinism-check rebuild must apply it identically):

```ts
for (const r of allRows) {
  (r as any).id = `${r.neighborhoodId}-${transactionKey(r)}`;
}
```

**Why this is provably correct, not just empirically lucky:** since Wave
0G-L1D, `transactionKey()` (from `lib/shadowRebuild.ts`) and the new
`Deal.id` fallback formula are the literal same function
(`buildTransactionIdSuffix(parcelNum, dealDate, price)`). Phase 3 of
`main()` — unchanged, pre-existing — already hard-asserts
`transactionKey()` is unique across all 59,305 rows (`throw`s otherwise,
before Phase 7 can ever write the file), computed independently of
whatever `.id` string happens to be stored. So `${neighborhoodId}-${transactionKey(r)}`
is guaranteed collision-free given that Phase 3 assertion holds — the
build cannot produce a colliding id and still complete successfully.

not a bug): Phase 7's sort key is `neighborhoodId|dealDate|id`, so
changing `id` values also changes tie-break order among same-
neighborhood/same-date rows. Order was never a semantic guarantee of this
file — no consumer in this repo relies on it (confirmed — see below).

## A real, critical bug caught by ECC review and fixed before commit

**ECC planner finding, applied:** `scripts/l1-import-v2-preview.ts` still
had the OLD SHA (`8bb67705...`) hardcoded as its `FROZEN_V2_SHA256`
constant. Since that script hard-throws `SHA_MISMATCH` on any deviation
from the pinned value, the regenerated file — the entire point of this
wave — would have been immediately rejected by the importer it exists to
unblock. Fixed: updated the constant to the new SHA, with a comment
explaining the supersession. Independently verified (a standalone
SHA-256 check, not by running the import itself — actually running the
import is a separate, distinct action from "regenerate and freeze," left
for its own explicit authorization) that the new constant now matches the
regenerated file exactly.

**ECC planner finding, applied:** added `supersededSha256` to
`data/v2-candidate/manifest.json`, pointing at the old, now-stale SHA —
`audit/launch/L0_V2_LAUNCH_CANDIDATE.md` and
`audit/launch/L1_SUPABASE_V2_PREVIEW_IMPORT.md` both reference the old
value by literal string; this gives a future reader an explicit,
in-manifest pointer confirming that value is superseded rather than
wrong.

## Verified: no consumer of `Deal.id` parses its internal structure

Given the new format contains `|`/`:` characters and internal hyphens
(from `parcelNum`, e.g. `"8006-47-1"`) that the old format never had, an
Explore agent searched all of `lib/`, `app/`, `scripts/`, and
`components/` (excluding tests and historical `audit/` one-offs) for any
code that parses/splits `Deal.id` expecting a fixed structure. Result:
**none exists.** Every usage is opaque equality/set-membership (dedup,
lookups, Postgres PK filters) or id *construction*, never parsing.
`ComparableDeal` (the type actually rendered in the UI) has no `id` field
at all — deal lists are keyed by array index, not `Deal.id`. No route or
filename in `app/` is built from `Deal.id`.

## Disclosed, not acted on (non-blocking, forward-looking notes)

- **ECC database-reviewer**, confirmed but not required: `id text primary
  key` is fine as-is for Postgres (no escaping/length concern; values
  flow through PostgREST as parameterized JSON, not interpolated SQL). A
  future `CHECK` constraint on the id's shape would be defense-in-depth,
  not a correctness requirement.
- **ECC planner**: if a future UI route ever builds a URL path segment
  from `Deal.id` (none currently does), the new id's `|` character would
  need `encodeURIComponent` — noted for whoever adds such a route, not
  actionable today.
- **ECC planner**: a `NULL_PARCEL_ROWS` diagnostic counter could be added
  to Phase 6 (currently `nullParcelNumCount`-style visibility exists in
  `lib/shadowRebuild.ts`'s dedup path but not in this build's own
  data-quality snapshot) — a nice-to-have, not required; this build's
  data has zero rows hitting `transactionKey()`'s documented residual
  limit (confirmed: `INVALID_DATE_ROWS=0` in Phase 6, so the
  null-parcel-AND-empty-date edge case never fires here).

## Scope note

This wave regenerated and re-froze the candidate file only. It did **not**
resume the actual Supabase preview import — that remains a distinct,
separately-scoped action (per the original L1 wave's own charter and this
engagement's standing "wait for explicit authorization before starting
the next wave" rule), now genuinely unblocked and ready to run via
`scripts/l1-import-v2-preview.ts` as-is.
